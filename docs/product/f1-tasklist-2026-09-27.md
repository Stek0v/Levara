## T1. Выключатель notebooks-роутов (Р2)

**Цель:** убрать `/notebooks*` из дефолтной поверхности, сохранив возможность
включения до удаления кода в Ф2.

**DoR:**
- Решение Р2 зафиксировано (✅ 2026-09-27).
- Точки входа известны: 10 роутов в `internal/http/api.go` (RegisterAPI),
  страница `webui/src/app/(dashboard)/notebooks/page.tsx`, навигация WebUI.

**DoD:**
1. Регистрация роутов обёрнута в флаг (предложение: `LEVARA_NOTEBOOKS`,
   дефолт `off`; невалидное значение → warning + off, не падение).
2. В дефолте `/notebooks*` отвечают 404 до auth/rate-limit миддлварей.
3. WebUI: страница скрыта из навигации при off; прямой заход даёт осмысленное
   состояние («функция отключена»), не бесконечный спиннер.
4. Тест internal/http: off — 404 на все 10 методов; on — 201/200; обе SQL не
   требуются (флаг выше слоя данных).
5. `make contract-check` проходит; сгенерированные контракты не правятся
   руками (контракт описывает полную поверхность, флаг — рантайм; сверить, как
   `make contract` поднимает сервер).
6. Флаг описан в deployment/profile-presets с пометкой «до удаления в Ф2».

**Corner cases:**
- Данные: выключатель не трогает таблицы `notebooks`/`notebook_cells` —
  ноутбуки владельца в Mac-БД остаются; решение об их судьбе — в T10.
- Прямой заход WebUI на /notebooks при off: рендер страницы с падающими
  fetch-ами — убедиться, что UX-состояние обработано.
- Контракт-генерация: если она снимает surface с живого сервера, сервер при
  генерации должен подниматься с включённым флагом, иначе контракт «сдувается».
- Флаг должен отсекать регистрацию до миддлварей, чтобы путь не попадал
  в auth-логи и метрики.

**Выполнено 2026-09-27:** флаг `LEVARA_NOTEBOOKS` (дефолт off; невалидное
значение → warning + off) в `internal/http/notebooks.go::notebooksEnabled`;
guard на все 10 роутов в `api.go::RegisterAPI`. Тесты
`notebooks_flag_test.go`: 404 на все 10 методов в дефолте, невалидное
значение → 404, флаг on → 200/201. PASS. WebUI: страница уже исключена из
навигации (sidebar-комментарий: «notebooks are an in-memory toy»), сама
страница остаётся до T10.

## T2. Связка personal → toolset core (Р1 финализация)

**Цель:** `LEVARA_PROFILE=personal` + пустой `LEVARA_MCP_TOOLSET` → эффективный
toolset `core` (13 инструментов). Приоритет источников: явный toolset >
personal-профиль > full. Без профиля поведение не меняется.

**DoR:**
- A+ вшит в `core` (✅ 2026-09-27, `pkg/mcp/tools_light.go`).
- Точки: `configuredMCPToolDescriptors` (internal/http/mcp.go), `ToolsetName`
  (pkg/mcp/tools_light.go), `pkg/profile` (нормализация профиля).

**DoD:**
1. Привязка реализована на уровне вызова (internal/http), НЕ внутри
   `ToolsetName` — инвариант теста `ToolsetName("")=="full"` сохраняется.
2. Матрица тестов: personal+пусто→core(13); personal+memory→memory;
   personal+full→full; solo_pro/team/enterprise+пусто→full; пусто+пусто→full;
   невалидный профиль → привязка НЕ применяется (только при валидном personal).
3. `admin/mcp/tools` и `admin/mcp/summary` показывают effective toolset и его
   источник (env / profile / default).
4. Оба MCP-транспорта (`/mcp` и датированный `/mcp/2026-07-28`) используют
   одну и ту же логику effective toolset.
5. product-ladder/profile-presets обновлены: таблица профиль→toolset.
6. Регресс-тест обратной совместимости: отсутствие обеих переменных = full.

**Corner cases:**
- Архитектурная ловушка: реализация внутри `ToolsetName` сломала бы
  `TestToolProfilesAreExplicitAndBackwardCompatible` — привязка живёт выше.
- personal + `LEVARA_LONG_HORIZON_RUNTIME=1`: long-horizon tools легитимны как
  явный выбор; фильтрация task_* из full уже работает, для core набора — не
  применимо (их там нет).
- Mac/Pi владельца: профиль не задан → full, поведение неизменно (покрыто
  матрицей).
- Датированный транспорт: проверить, что он не дублирует логику выбора.

**Выполнено 2026-09-27:** `internal/http/mcp_toolset.go` —
`EffectiveMCPToolset` (явный env > personal > full; сравнивается сырое
значение `LEVARA_PROFILE`, потому что `profile.Normalize("")=="personal"` —
иначе пустой профиль сузил бы toolset всем); единая точка
`configuredMCPToolDescriptors` покрывает оба MCP-транспорта и `/admin/mcp/tools`;
`/admin/mcp/summary` отдаёт `toolset`/`toolset_source`/`advertised_tools`;
`toolRuntimeStats` и startup-лог `main.go` используют тот же резолвер.
Тесты `mcp_toolset_test.go`: матрица 9 кейсов + инвариант 13 инструментов
(core c supersede/delete, без consolidate/workspace/task/chat) + full-дефолт;
`pkg/mcp` инвариант ToolsetName — PASS.

## T4. Smoke чистой установки (Р5)

**Цель:** измеримое подтверждение метрик запуска: 10 минут, 3 команды, 13
инструментов.

**DoR:** T1–T3 смержены.

**DoD:**
1. Скрипт (python, JSON-RPC по /mcp: initialize → session → tools/list →
   wake_up) + ручной рецепт для человека.
2. Замер wall-clock; результат в docs/testing.md: дата, ревизия, окружение,
   время, число инструментов.
3. Два сценария: «чистая машина без моделей» (без embed) и «Mac с локальным
   embed-server» — метрики для обоих.
4. Если метрика не достигнута — блокеры фиксируются как задачи (валидный
   результат, не провал).

**Corner cases:**
- MCP-handshake нетривиален (initialize → session id header → tools/call);
  скрипт должен это покрывать, иначе «tools/list» не честный.
- Замер времени не должен включать скачивания моделей/образов в середине.
- tools/list при toolset по умолчанию (full) посчитает не 13 — smoke обязан
  явно выставлять personal/core (это и есть проверка T2).

**Выполнено 2026-09-27:** `scripts/smoke_personal.py` — настоящий
MCP-handshake (initialize → Mcp-Session-Id → tools/list → wake_up →
save/recall). Прогон на чистой SQLite: **17/17 PASS**, build 9 с, старт ≤2 с,
handshake 0,02–0,03 с. Smoke нашёл и закрыл дефект: audit-лог писал сырой
toolset из env («full») вместо эффективного («core») — исправлено
`effectiveMCPToolsetName`. Результаты с датой и границами покрытия — в

ручные шаги clone/.env/MCP-конфиг и не измерялись end-to-end на чужой машине.

2. Схема происхождения и ACL: писатель обязан проставлять owner/team/dataset

5. Решение владельца по варианту зафиксировано в доке.

**Corner cases:** шумная таксономия бустит не то → деградация recall
(невидимая, как stale-факты) — потому gate обязателен; производительность

VSA-boost живёт и без DCD — маршруты лишь буст, не условие.
